2INSTRUCTION FILES

One file. Every session. Zero policing.

“You write your coding standards once in AGENTS.md. Every session in your repo follows them — for new hires, contractors, and senior engineers alike.”
  • AGENTS.md at repo root — always-on for every session.
  • /init + tell it to create AGENTS.md.
  • No one needs to invoke it — it's automatic.
  • Encode team standards without policing every PR.
copilot · initialize
> /init create AGENTS.md for this repo ✓ Created AGENTS.md at repo root Edit it to capture your team's standards. # AGENTS.md — your team's always-on rules ## C# backend use nullable refs; no #pragma warning without ticket ## TypeScript frontend strict mode always; no any in reviewed code ## Commits Conventional commits required
Highest-leverage thing a team lead can set up.
5 minutes of writing, permanent impact.
Why AGENTS.md, not copilot-instructions?
GitHub Copilot generates .github/copilot-instructions.md by default — that's Copilot-only. AGENTS.md is an open standard recognised by Copilot, Claude Code, Cursor, and more. Write once, work everywhere.
/p2/agents-md 11 / 33
2SCALING UP

One AGENTS.md can't
capture a real project.

The problem
Architecture. API conventions. Deployment. Security. Domain logic. Style guides.
Stuff all of that into one file and you get a wall of text AI has to read every single turn.
The pattern
AGENTS.md becomes an index.
A short file pointing to detailed docs in docs/. AI loads the index always — and pulls in detail only when it's relevant to the task.
/p2/index-problem 12 / 33
2INDEXING PATTERN

Index in the root. Detail in docs/.

📁your-repo/
├─📄AGENTS.mdindex → points to docs
├─📁docs/
│ ├─📄architecture.md
│ ├─📄csharp-conventions.md
│ ├─📄typescript-style.md
│ ├─📄api-design.md
│ └─📄deployment.md
├─📁src/
└─...
How it reads
Every session loads AGENTS.md (small, fast). When a task references APIs, AI follows the pointer to docs/api-design.md — and only then.
Why it works
  • Keeps AGENTS.md short and editable.
  • Detail docs stay discoverable.
  • Context isn't bloated with irrelevant rules.

3WHY IT MATTERS

Three reasons orchestration
beats one big agent.

01 / Context
Isolation
Each policy sees only its own checks/*.md. No cross-contamination, no wasted context.
02 / Domain
Specialization
Security expertise lives in the security sub-agent. Perf lives in perf. No generalist compromises.
03 / Speed
Parallelism
Four policies run concurrently. Review time ≈ slowest policy, not sum of all.
When to reach for it
Multi-step workflows across domains · tasks bigger than one agent's context · reusable, composable specialists.

5INTEGRATION CHOICES

Two paths. Pick the right one.

CLI
Lightweight & composable
  • Text in, text out — matches how LLMs think.
  • Self-describing via --help, pipeable.
  • Skills wrap CLI workflows into reusable procedures.
install
$ az extension add --name azure-devops $ az devops configure --defaults \ organization=https://dev.azure.com/IHIS-HIP
Requires the CLI to be pre-installed on every machine. Plugin can't guarantee it's there.
MCP Server
Self-contained & distributable
  • 88 tools — test plans, code search, security alerts.
  • Auto-installs via npx — zero manual setup.
  • Ships inside the plugin. One install, everyone gets it.
.mcp.json
"ado": { "type": "stdio", "command": "npx", "args": ["-y", "@azure-devops/mcp", "IHIS-HIP"] }
Heavier runtime. May register more tools than your agent needs.
How to decide: Need to distribute via a plugin? MCP — it ships self-contained. CLI already installed across your org? CLI + Skills — lighter and composable. Either way, skills augment both.

The mental model

One plugin.json. Every pillar. One install.

Pillar mapping
"mcpServers"→ Pillar 5 · external connectors "agents"→ Pillar 3 · orchestration "skills"→ Pillar 4 · including CLI wrappers triggers→ Pillar 1 · automation SKILL.md + checks→ Pillar 2 · guardrails
Where does CLI fit?
CLI commands live inside skills. A skill wraps az devops calls into a reusable procedure — the plugin ships the skill, the CLI does the work.
MCP ships self-contained. CLI ships via skills. Both compose into one plugin.
plugin.json · code-review
{ "name": "code-review", "description": "Framework + policy plugins", "mcpServers": ".mcp.json", "agents": [ "./agents/code-reviewer.agent.md" ], "skills": [ "./skills/design-patterns", "./skills/hims-ads-policy", … ] }
